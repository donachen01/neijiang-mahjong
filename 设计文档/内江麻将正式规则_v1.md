## 1. 文档说明

本文档不是“唯一官方标准文本”，而是基于公开规则资料、平台玩法说明与地方玩法特征，整理出的**工程开发正式规则 v1**。
其中每条规则分为三类：

- **已确认**：当前可直接作为开发规则落地
- **程序默认值**：公开资料未完全统一，但为了开发推进，先采用的默认实现
- **待后续确认**：先保留接口，后面可由你再拍板修正

本工程维护口径：

- **代码为准**：当文档与当前实现不一致时，以当前工程代码为准，并应立刻回写本文档。
- **结算代码优先级最高**：番型、番值、封顶、自摸附加分、报叫额外赔付、杠分、查叫赔付，以 `scripts/core/fan_resolver.gd`、`scripts/core/score_resolver.gd`、`scripts/core/rule_config.gd` 为准。
- **AI 决策代码优先级最高**：电脑玩家弃牌、碰、杠、胡、报叫、报杠、自摸/暗杠/补杠等决策，以 `dotnet/AI.Core` 内 C# 引擎为准。
- **前端不替 AI 做决策**：Godot 前端只负责合法候选、状态机、动画、UI 与执行 C# 返回结果，不得把 C# 的“碰”改成“杠”，也不得替 C# 选择弃牌。

## 6. 报叫规则

### 6.1 报叫触发
- **中高置信，按已确认落地**：起手若已听牌，可 `报叫`
- **中高置信，按已确认落地**：庄家不可报叫

### 6.2 报叫后效果
- **中高置信，按已确认落地**：报叫后 `不能换牌`，即进入锁手状态
- **中高置信，按已确认落地**：若出现可胡机会，可自动胡牌

### 6.3 报叫附加输分
- **中高置信，按已确认落地**：报叫后如果别人先胡，报叫者需要 `多输一番`

### 6.4 报杠细则
- **程序默认值（高可信）**：若玩家在报叫当下，存在**可杠且杠后补牌、再打一张后仍不破坏报叫听口**的杠牌，则允许同时声明 `报杠`
- **程序默认值（高可信）**：`报杠` 只允许登记那些**不会破坏报叫牌型**的杠牌
- **程序默认值（高可信）**：报叫后，凡是已经声明过的 `报杠` 牌，后续在牌局进行中若条件满足，可执行对应杠牌
- **程序默认值（高可信）**：若某张牌在报叫时本来可以报杠，但玩家**没有报杠**，则后续该张牌**不能再杠**
- **程序默认值（高可信）**：若玩家选择 `不报杠`，则报叫后整局按锁手处理，不再新增杠牌选择

### 6.5 报杠范围约束
- **程序默认值**：报杠的核心判断不是“当前能不能直接杠”，而是“这张牌是否属于**预先申报且不影响报叫听口**的合法杠牌”
- **程序默认值**：若某个杠动作会改变听牌结构、减少听口、破坏已报叫牌型，则该杠**不得报出**
- **程序默认值**：程序实现时，应对每个候选杠牌做一次模拟：`杠 -> 补牌 -> 弃一张`，只要仍保持报叫状态，才允许列入报杠项

### 6.6 起手暗杠的特殊处理
- **程序默认值（高可信）**：若玩家起手既满足报叫，又存在暗杠机会，则不能把“起手可暗杠”直接视为自由开杠
- **程序默认值（高可信）**：应先判定该暗杠是否属于“报叫后仍不破坏听口的报杠项”；若不是，则不能在报叫状态下执行该暗杠
- **程序默认值**：若玩家放弃胡牌/放弃普通开杠而选择报叫，则后续只按已声明的报杠集合执行，不得临时新增杠项

### 6.7 仍保留的实现接口
- **待后续确认**：内江本地是否把 `报杠` 单独计番，当前默认 `不额外计番`
- **待后续确认**：报叫后是否允许所有类型的杠都通过“报杠”申报，还是只允许其中部分类型
- **待后续确认**：若报杠后补牌直接成胡，是否仅记杠上花，还是与报叫相关番型叠加，当前按番型累加框架预留接口

### 6.8 程序默认值
- **程序默认值**：首版实现为“报叫后锁手，不允许改变听口结构的主动调整”
- **程序默认值**：在此基础上，增加“报杠白名单”机制：只允许执行报叫时已申报、且经模拟验证不破坏听口的杠牌

### 6.9 当前代码口径（以 C# 报叫专线为准）
- **已接入实现**：报叫玩家进入 C# `NeijiangBaoJiaoActionEngine` 专线。
- **已接入实现**：报叫后弃牌为“摸什么出什么”，C# 只允许打出本轮摸牌，前端不得替换为其他手牌。
- **已接入实现**：报叫后自摸必胡，点炮必胡。
- **已接入实现**：报叫后非胡、非报杠响应只能过，不能再碰牌改形。
- **已接入实现**：报叫后摸到或遇到已声明的报杠白名单牌时，C# 按强制报杠处理。
- **已接入实现**：AI 是否声明报叫、声明哪些报杠项，由 C# `NeijiangBaoJiaoDecisionEngine` 评分决定；Godot 只负责构造听牌与报杠候选并执行 C# 结果。
- **已确认**：若七对路线成立，碰与任何杠都会破坏七对；因此七对类牌型不能碰，也不能暗杠、明杠、补杠。
- **已接入实现**：人类报杠选择界面只展示合法候选牌面，最多横排 4 张；默认选中，点牌切换，右上角关闭即写入选中的 `bao_gang_keys`，不再用文字列表和底部确认/取消按钮。

## 8. 番型规则

### 8.1 当前项目记分口径
当前项目按“番档折算分值”实现，基础分值表为：

- `1 番 = 1 分`
- `2 番 = 2 分`
- `3 番 = 4 分`
- `4 番 = 8 分`
- `5 番及以上 = 16 分`

### 8.2 当前项目番型 / 番档口径
- **已确认**：`平胡` = 1 番 = 1 分
- **已确认**：`卡二条` = 额外 +1 番，因此平胡卡二条 = 2 分
- **已确认**：`报叫` = 额外 +1 番
- **已确认**：`归` = 每个额外 +1 番
  - 判定口径：结算时统计“最终手牌 + 副露碰杠牌 + 胡的那张牌”中的同牌数量；同一牌达到 4 张才算 1 个归，每满 4 张同牌算 1 个归。
  - 杠牌雨钱与归番型相互独立：杠税记录本身不直接加归，只有结算牌组实际凑满 4 张同牌才加归。
- **已确认**：`杠上花` = 额外 +1 番
- **已确认**：`抢杠胡` = 额外 +1 番
- **已确认**：`杠上炮` = 额外 +1 番
- **已确认**：`海底` = 额外 +1 番
- **已确认**：`大对子` = 3 番 = 4 分
- **已确认**：`清一色` = 3 番 = 4 分
- **已确认**：`暗七对` = 3 番 = 4 分
- **已确认**：`地胡` = 额外 +4 番，定义为“闲家首轮胡庄家第一张出牌”，番数按 5 番封顶
- **已确认**：`天和` = 额外 +4 番，番数按 5 番封顶
- **已确认**：`龙七对` = 4 番 = 8 分
- **已确认**：`清对` = 4 番 = 8 分
- **已确认**：`清七对` = 4 番 = 8 分
- **已确认**：`青龙七对` = 5 番 = 16 分

当前代码番型选择顺序以 `FanResolver._resolve_neijiang_win_fans` 为准：

1. `清七对 + 归` 判为 `青龙七对`，基础 `5 番`
2. `清七对` 判为 `清七对`，基础 `4 番`
3. `清一色 + 大对子` 判为 `清对`，基础 `4 番`
4. `七对 + 归` 判为 `龙七对`；1 个归为 `4 番`，2 个及以上归按当前代码进入 `5 番` 封顶档
5. 普通 `暗七对` 判为 `3 番`
6. 普通 `清一色` 判为 `3 番`
7. 普通 `大对子` 判为 `3 番`
8. 其余为 `平胡`，基础 `1 番`

当前代码牌型判定细则：

- `暗七对 / 龙七对 / 清七对 / 青龙七对` 必须无副露，最终 14 张必须全部由对子或 4 张同牌拆成七个对子；只要已经碰或杠，就不能再算七对类。
- `大对子` 要求副露只能是碰或杠，手牌部分可拆成刻子加一对。
- `清一色` 会把手牌与副露一起统计，只要全部属于同一门且非空即可成立。
- `卡二条` 要求胡牌张为 `2条`，且存在一种和牌拆解让 `2条` 位于 `1条-2条-3条` 的中间；七对类默认不算卡二条。
- `归` 统计最终手牌、胡牌张与副露牌，同一牌达到 4 张算 1 个归；杠牌雨钱本身不直接等于归，必须最终牌组凑满 4 张。

### 8.3 叠加方式
- **程序默认值**：当前版本按“基础牌型番档 + 事件附加番档”累加
- **程序默认值**：`自摸` 不再作为翻倍项，而是**在结算分值上额外 +1 分**

### 8.4 封顶规则
- **已确认**：当前项目按 **5 番封顶**
- **程序默认值**：5 番对应基础胡牌分值 `16 分`，但 `自摸 +1`、报叫额外赔付等附加分在此基础上继续正常结算

### 13.4 前后端交互模式
- **合法候选在 Godot**：前端根据当前规则生成可胡、可碰、可杠、报杠白名单、暗杠/补杠候选，并把候选编码成 C# 可读的 `tileType`。
- **决策在 C#**：AI 弃牌、反应、报叫、报杠、自摸、暗杠、补杠、地狱挑战压制策略均由 C# `NeijiangAiFacade` 及其引擎返回动作。
- **前端只执行**：Godot 执行 C# 返回的 `Discard / Hu / Peng / Gang / Pass`，并处理动画、UI、状态迁移、结算触发。
- **不得前端覆盖**：若 C# 返回碰，即使同张也能杠，前端不得擅自升为杠；若该选择不合理，应修 C# 评分或 C# 参数。
- **报叫报杠例外说明**：前端可以过滤规则上不合法的报叫后碰牌、非白名单杠牌，但“AI 是否报叫、报哪些杠、摸到报杠是否执行”的最终动作仍由 C# 专线决定。
- **传输模式**：Godot 优先通过内嵌/host C# runtime 请求，必要时退回 CLI JSON 调用；无论传输方式如何，决策口径必须一致。
- **路线规划诊断**：C# 出牌结果会返回 `routePlan`，候选弃牌会返回 `routePlanPrimary / routePlanScore`。这些字段只用于调试、复盘与 UI 展示，不允许 Godot 据此另行改动作。
- **路线是软权重**：七对、大对子、清一色等路线不能在排序层硬压总分；若路线候选明显更慢、更危险或净分更低，必须让位给更快下叫、更低点炮风险的候选。
- **当前权重口径**：AI 出牌综合分按 `expectedValue * 100` 折算；路线、下叫速度、点炮风险、防守后验、碰杠收益都必须进入同一综合分比较。普通路线保护不能绕过总分排序。
- **七对保护量级**：七对路线下拆对子/刻子会强降权，但若弃牌后能直接下叫，惩罚会显著缩小，允许“能下叫先下叫”覆盖普通七对保护。
- **碰杠量级**：碰牌必须服务成叫速度或明显结构收益；碰后首打同张、七对已听、七对路线禁碰都会强降权。杠牌必须同时满足雨钱收益、成叫速度、首打安全和抢杠胡风险；七对路线禁所有杠。
- **防守量级**：点炮危险度会先折算为点炮概率，再进入净分期望；中后期、未成叫、窄听、对手后验高时会额外放大防守权重。极危同速和牌墙极少时允许硬防守 override，但不能随意拆掉已有下叫。
- **七对约束**：`暗七对 / 龙七对 / 清七对 / 青龙七对` 路线成立时，C# 会把碰、明杠、暗杠、补杠作为破坏七对处理；是否放弃七对改走平胡或大对子，也必须由 C# 评分得出。
- **清一色潜力**：当某一门达到 `10+`，且异门 `<=3` 时，C# 会把清一色作为主线候选；候选弃牌也会把强清色胚子纳入番值期望，优先清异门，但不能为了伪清一色错过直接下叫。
- **归 / 四张同牌保护**：四张同牌即使打一张仍剩刻子，也会失去归、杠材和高番潜力。C# 当前按高价值资源保护，前中期拆四张同牌约 `-1800` 综合分，后期约 `-1200`，除非速度、收益或安全综合分明确更优。
- **给碰不点炮口径**：地狱挑战也必须保留真实麻将互动。若 AI 自己能下叫或保叫，且给本家只会碰、不胡、不杠、本家也不能因此立刻下叫，则允许打给本家碰；不得为了防普通碰把自己拖成未叫。
